## decision-0001: Scaffold

- Date: 2026-11-13T12:52:15+05:30.
- Choice: template `react`, one context `primary`, one route `home` to screen `home`, no storage or services.
- Evidence: generated by `genesis-applet create`; nothing verified yet.

## decision-0002: Feasibility spike on protected media

- Date: 2026-11-13.
- Finding: signed-in open.spotify.com requires Encrypted Media Extensions with Widevine. The Genesis shell denies `RESOURCE_PROTECTED_MEDIA_ID` in its WebView permission handler (it grants only camera and microphone), so Spotify replaces the whole web player with "Playback disabled", not just the audio. Browsing, Library and Search are therefore blocked too, not only playback.
- Spike: a local, uncommitted shell patch that grants protected media made the signed-in mobile web player render (Home, album pages, bottom tabs). On the emulator, playback then failed: the Widevine L3 license was added, and Chromium's audio renderer reported `PIPELINE_ERROR_DECODE`. This looks like an emulator limitation of decrypting audio, but that is not confirmed; real hardware was not used. The patch was reverted.
- Needed platform capability: the shell grants protected media to pages on an applet's declared origins (or on origins the applet asks for), as a public contract applets can rely on. Media playback may also need trusted input to count as a user gesture (`setMediaPlaybackRequiresUserGesture(true)`); not yet tested because playback did not start on the emulator.
- Sanitized reproduction: install an applet whose origin is https://open.spotify.com, sign in, and reveal the website. With the current shell it shows "Playback disabled". With protected media granted it renders; pressing Play on an album on an Android 17 arm64 Google Play emulator image gives `PIPELINE_ERROR_DECODE` after the license is added.
- Choice: applet work paused at the user's request before the platform decision. Open questions: whether to make the platform change, and whether to check playback on a physical phone (requires explicit permission).

## decision-0003: Playback probe

- Date: 2026-11-13T13:48:42+05:30.
- Context: the shell now grants protected media to website pages, so the signed-in web player renders and plays on a phone with Widevine L1. The emulator still fails to decode, so device checks use a phone.
- Choice: a minimal probe, not PRD screens: reader `nowPlaying` and command `setPlaying`, shown as a strip on screen `home`.
- Trusted input: Genesis requires a user gesture before a page plays sound, as browsers do. A synthetic click is not a gesture; `input: "trusted"` gives the hidden page user activation. Verified: Play from the applet starts audio.
- Play state from the icon: the mobile web player's button has no `aria-label`. Its icon has two subpaths while playing (Pause) and one while paused. A progress element's `--animationPlayState` also reports running or paused; the probe uses the icon because it belongs to the button the command clicks.
- Spotify Connect: when Spotify counts another device (often an earlier copy of this page) as the active player, a modal "You are listening on … / Continue / Listen on this phone" covers the mini-player, and the bar's second line names the device. A plain click then fails with `NOT_ACTIONABLE`. The command chooses "Listen on this phone" first. Taking playback over left the page paused, so only Play presses the button afterwards. The modal container `[data-testid=client-modal-contents]` stays in the DOM with class `closed`, so the probe checks for an open container with that button.
- Not available to the applet: Android WebView has no `navigator.mediaSession`, so the website cannot publish notification or lock-screen controls. Audio stops when Genesis frees background applets. Both are platform follow-ups.

## decision-0004: Milestones for the PRD build

- Date: 2026-11-13.
- Choice: at the user's request, the PRD build runs in six milestones, each built, verified on the phone and committed before the next: (1) app frame and player; (2) Home, Album, Playlist and Artist; (3) Search, Browse and genre hubs; (4) Library, Liked Songs, track menu, add to playlist and toasts; (5) Podcasts, Audiobooks, Devices and Lyrics; (6) Profile, the Settings the website exposes, and a blocked entry with its reason for each PRD item the website cannot support.
- Frame: Now Playing and Your Library are overlay screens, so they open over whichever website page is current; Home is a routed screen for `/`. Now Playing opens the website's full player while it shows, because shuffle, repeat, previous and the progress bar exist only there, and closes it on leave.
- Reading the mini-player: its carousel draws the previous, current and next tracks side by side, each as a title span followed by an artists span. The current track is the first slide whose left edge is inside the bar. This also gives "Next up", the only queue entry the web player exposes.
- Repeat: the button's label names the next state ("Enable repeat", "Enable repeat one", "Disable repeat"), so the current state is read from it and `setRepeat` presses as often as the cycle needs.

## decision-0005: Seeking with arrow keys

- Date: 2026-11-13.
- Finding: the full player's progress bar seeks on a real tap at a point. Genesis's trusted click always taps an element's center, a synthetic pointer sequence is ignored, and filling or setting the hidden range input's value does not commit (a forced fill also left the page unable to play until it reloaded).
- Choice: `seek` presses ArrowRight or ArrowLeft in the hidden range input as trusted keys. Each press moves five seconds. The input is controlled, so a press sent before Spotify redraws steps from the old value; after each press the command waits until the input's `aria-valuetext` leaves the previous position. Locators may not test `value`, so the wait uses `aria-valuetext`. At most 60 presses, each about 0.4 s.
- The applet's own range commits on its native `change` event, which fires once on release, after the last value. A tap's `pointerup` comes before the value changes.
- Platform note: a trusted click at an offset inside an element would make seeking one tap. Not requested here.

## decision-0007: Now Playing rises and falls

- Date: 2026-11-15.
- Choice: the kit's motion gains `rise` and `fall`. A place marked `full` (Now Playing) enters by sliding up over the app and leaves by sliding down, while the screen under it holds still, as the Android app's player does. Every other change keeps the kit's push, pop and fade through. Reduced motion shows the change at once.

## decision-0008: Outcomes in toasts, Undo for removals

- Date: 2026-11-15.
- Choice: every tapped command shows busy until Spotify answers (at least 800 ms, one write per tap), then reports in the toast: the reason when it failed, "Spotify didn't confirm that" when the page never showed the change, and a confirmation when one helps. The inline notices on Now Playing, entity pages and Search are gone. Removing a song from Liked Songs, an album or playlist from Your Library, and unfollowing an artist offer Undo, which sends the opposite command and fails the toast's Undo when Spotify does not confirm it.

## decision-0009: No Undo for recent searches

- Date: 2026-11-15.
- Choice: removing one recent search and clearing them all confirm with a toast and offer no Undo. The website has no way to put a recent search back except searching for it again, which would also change the results page.

## decision-0010: Where refresh applies

- Date: 2026-11-15.
- Choice: Home, category hubs, album, playlist and artist pages and Browse all have pull to refresh and a labeled Refresh button, both reloading the page. Search results do not: typing already refreshes them, and pulling would fight the keyboard. Now Playing and Your Library do not: the player follows Spotify live, and the library has one fixed row.

## decision-0011: Hold the page while it plays

- Date: 2026-11-17.
- Problem ID: `applet-performance` · Problem: Find what makes page switches, loads and like/save actions lag in the built applets · Spirit animal: 🐆 Leopard
- Origin: the builder, from a phone check.
- Finding: Genesis now rests a covered page the applet is not using. With the Spotify page resting, audio kept playing, but the end of a track was followed by 13 seconds of silence before the next one started, and the mini-player showed the old track for minutes.
- Choice: the app holds the `primary` context at `running` while `nowPlaying` reports that this page plays (`playing` and not `elsewhere`). The hold ends when playback pauses or moves to another device, so an idle Spotify costs nothing. Every control is a call, which wakes the page by itself.
- Choice: a Home or hub shelf reads at most 20 tiles. A longer row was re-sent whole on each change of the list.
- Journeys affected: play, then browse; track change in the background of the applet.

## decision-0012: Show kept pages first, keep Home, window the track list

- Date: 2026-11-18.
- Problem ID: `applet-performance` · Problem: Find what makes page switches, loads and like/save actions lag in the built applets · Spirit animal: 🐆 Leopard
- Origin: agent choice while upgrading the applet to Genesis's runtime speed work.
- Choice: screens keep drawing content whenever there is data, fresh or kept, and read loading, empty and failed from the watch's data state (`watchStatus`).
- Choice: Home's watches set `persist`, because Home is the first screen. `nowPlaying` is not kept: the playback hold follows it, and a kept "playing" from the last run would hold a page that plays nothing.
- Choice: when the router reports no account and the applet last saw one, the applet calls `forgetCached`. It remembers only "signed in" or "signed out" in its own storage, so a signed-out start does not forget each time.
- Choice: album and playlist rows use `VirtualList`, because a long playlist's rows accumulate as the list end loads more, and every row has the same 60 px height, so Back lands where it left. An artist's Popular rows are a few numbered rows and stay a plain list. Search results, shelves and hubs stay plain: they are short.
- Journeys affected: cold start, albums and playlists, sign out.

## decision-0013: Navigation keeps the music

- Date: 2026-11-19.
- Problem ID: `spotify-official-app-parity` · Problem: Make the Spotify applet match the official Spotify Android app in features and interaction speed · Spirit animal: 🐬 Dolphin
- Origin: the developer approved the Genesis capability on 2026-11-19, after the gap list and the web player probe.
- Finding: `navigate({ url })` clicks the site's link for the URL and loads the URL as a new document when the site does not take the click within 1000 ms. Spotify's Home cards do not take it: they load a new document even on a real finger tap on the revealed website. The new document stops the audio, and the next Play starts the previous track from 0:00 (gaps P-01, P-02, N-01). The site takes its own tab links, track and artist links, and the cards on album, artist, playlist and Search pages in one document. A history push followed by a `popstate` event renders any path in the same document with the audio playing, but a page module may not do that.
- Choice: a general Genesis capability. When an applet navigates a context to a same-origin URL and the site does not take the link, Genesis tries a same-document route (a history push and `popstate`) before a full load, and falls back to the load when the page does not change. The applet relies on it and changes nothing for it. Until it ships, Home cards stop the audio.
- Choice: the applet keeps one context, `primary`. A second page that only plays would be a second Spotify Connect device and would take playback over from the first.
- Journeys affected: open an album, playlist or artist from Home while a track plays; Back to Home; the mini-player during navigation.
- Evidence: the applet walk and the web player probe in [the gap list](investigation-parity-gaps.md). The two-page behaviour was not tested on the phone.

## decision-0014: Seek by a tap at a point

- Date: 2026-11-19.
- Problem ID: `spotify-official-app-parity` · Problem: Make the Spotify applet match the official Spotify Android app in features and interaction speed · Spirit animal: 🐬 Dolphin
- Origin: the developer approved the SDK option on 2026-11-19.
- Finding: the arrow-key seek of decision-0005 never landed on the phone: the time label froze, and the command ran 9.7 to 14 s and ended with DEADLINE (gap P-03). The page's audio element is detached and out of a page module's reach. The full player's progress bar (`[data-testid=npv-container] [data-testid=progress-bar]`) seeks to the point of a touch: a touch pair at a fraction of its width seeks to that fraction of the duration in 157 to 202 ms. The SDK's tap gesture always taps an element's centre.
- Choice: the SDK tap gesture gains an option to tap at an offset inside the target. `seek` becomes one write: one tap on the progress bar at the target's fraction, with the website's full player open. It still waits until the page shows the new position.
- Supersedes: the slow-seek part of decision-0005 (arrow-key presses, five seconds each, up to 60 presses). The applet's own range still commits once on release.
- Journeys affected: seek from Now Playing; Next during a seek.

## decision-0015: Skip through the mini-player carousel

- Date: 2026-11-19.
- Problem ID: `spotify-official-app-parity` · Problem: Make the Spotify applet match the official Spotify Android app in features and interaction speed · Spirit animal: 🐬 Dolphin
- Origin: part of the playback architecture the developer approved on 2026-11-19; the route comes from the web player probe.
- Finding: the website's mini-player holds a scroll-snap carousel (`[data-testid=floating-now-playing-bar] > img + div`) with the previous, current and next tracks. Scrolling it to its end plays the next track (audio in 148 to 191 ms, title in 225 to 278 ms); scrolling it to its start goes back. Five scrolls 250 ms apart advanced one track, then the row stuck off centre with stale titles. Spotify has no keyboard shortcut or media session for skips.
- Choice: `skip` scrolls the carousel with a page-control scroll to its end (Next) or its start (Previous), one skip per command, and is satisfied when the track changes and the row is centred again. When the carousel is missing or does not move, `skip` falls back to the full player's skip buttons. Skip no longer opens the full player first.
- Journeys affected: Next and Previous from the mini-player and from Now Playing; a burst of skips.

## decision-0016: Position from the bar's style variables

- Date: 2026-11-19.
- Problem ID: `spotify-official-app-parity` · Problem: Make the Spotify applet match the official Spotify Android app in features and interaction speed · Spirit animal: 🐬 Dolphin
- Origin: part of the playback architecture the developer approved on 2026-11-19; the route comes from the web player probe.
- Finding: the `player` value read the position from the full player's range input every second, so the whole record was sent and Now Playing rendered again each second (gap O-06). The website's progress element carries `--finalAnimationDuration` (the duration in ms), `--animationDelay` (minus the position in ms) and `--animationPlayState` (`running` or `paused`), and changes them only when the position jumps or the play state changes.
- Choice: a reader takes the position, the duration and the play state from those style variables, which change rarely, and the applet runs a local clock from them while playing. The range input is no longer read for the position, and the full player need not be open to show progress.
- Journeys affected: the progress line on the mini-player, the progress bar on Now Playing.

## decision-0017: Playback controls answer at once

- Date: 2026-11-19.
- Problem ID: `spotify-official-app-parity` · Problem: Make the Spotify applet match the official Spotify Android app in features and interaction speed · Spirit animal: 🐬 Dolphin
- Origin: part of the playback architecture the developer approved on 2026-11-19.
- Finding: the title, the art and the skip waited for Spotify's page (Next 1021 ms against the official 300 ms), controls stayed busy for at least 800 ms and dropped taps, identical pending calls merged in the SDK, and a call during a load failed at once (gaps P-04, P-06 to P-09).
- Choice: one playback store merges what Spotify last reported with what the user asked for since, and every playback control draws from it. A tap changes the store and the screen in the same frame, then sends its command. Controls are never disabled for busy. Taps queue per command; opposite taps (Play then Pause, Next then Previous) cancel before they are sent. An intent that Spotify has not confirmed after 6 s falls back to what Spotify reports, with one toast for the whole burst.
- Supersedes: the busy-until-answer part of decision-0008 (busy for at least 800 ms) for playback controls. Non-playback actions such as Follow keep it, and toasts and Undo stay as decision-0008 says.
- Journeys affected: Play, Pause, Next, Previous, Shuffle, Repeat and Save on the mini-player and Now Playing; a track row tap.

## decision-0018: Features the web player lacks stay open

- Date: 2026-11-19.
- Problem ID: `spotify-official-app-parity` · Problem: Make the Spotify applet match the official Spotify Android app in features and interaction speed · Spirit animal: 🐬 Dolphin
- Origin: part of the playback architecture the developer approved on 2026-11-19; the route comes from the web player probe.
- Finding: the Free mobile web player has no Your Library page (its tab shows an upsell), no queue view, no Add to queue and no Add to playlist in its track menu (which holds Like, Share and View track, artist and album), and no image for the next track in its bar.
- Choice: these are recorded as open gaps (F-02, F-04, F-05, F-06 and the art part of P-06), and the applet builds nothing against the website for them. Liked Songs stays the website's own page. After a Next tap the applet shows the next track's title at once and keeps a neutral tile until the art arrives.
- Journeys affected: Your Library, the queue, the track menu, Now Playing after Next.
